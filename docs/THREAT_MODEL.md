# Threat model

## What each party learns

- Community admins and the adapter. They learn a platform identity (for example a Discord user id) and an unlinkable nullifier. The intended proof does not disclose the voting key or selected node. Platform activity and network metadata can still reveal or suggest identity.
- The gateway. It learns the platform account the challenge was minted for (the B1 relay fix binds that account into the signal hash the proof commits to, and the local spend record keeps it for idempotent re-grants; the Platform-backed nullifier store deliberately omits the account from its documents, so it is retained only in memory for the request there), a per-request nonce, and the nullifier. From the proof itself it learns no address, no voting key, and not which node. The one place this can leak is the NETWORK PATH, not the cryptography, since a request reveals the source address to the gateway. The account-bearing calls (the challenge and the proof submission to verify) are relayed by the adapter, so the gateway sees the adapter's address there. But the two-tier prover contacts the gateway directly on its public reads: registration posts to `/v1/register`, and the per-epoch prove fetches `/v1/members` to build its path. On both, if the prover runs on the masternode, the source address is the node's advertised service address, which is in the public masternode list, and a gateway operator can join the two to learn which node this is. Both two-tier steps should therefore run over an anonymizing path (for example Tor) or from a machine whose public egress address cannot be matched to the node (behind the same address is not separation). The prover prints this warning on a non-loopback gateway, and `docs/MEMBER_GUIDE.md` states it. Single-tier proving contacts no gateway at all. The gateway also observes request timing, which fronting infrastructure hides only if it deliberately batches or delays, not merely by being present.
- The oracle. It reads only public chain data, so it learns nothing private.
- A network eavesdropper. From the cryptography it links nobody to a node, since the proof reveals nothing and the traffic is https on the supported configuration. Content confidentiality holds only when the gateway URL is https, which the adapters and prover enforce for a remote host unless `MNO_GATEWAY_ALLOW_HTTP=1` deliberately relaxes it, and the gateway calls refuse redirects (`redirect: "error"`) so an https endpoint cannot bounce the request onto a plaintext or foreign origin. Even with content hidden, an eavesdropper on the path sees network endpoints, which https does not hide, so the two-tier prover's direct calls to the gateway (registration and the per-epoch members fetch) expose the source address. Run on the masternode, that is the node's own advertised address, and the eavesdropper can match it to the public list exactly as the gateway operator can. The same mitigation applies: run the two-tier prover over an anonymizing path. Single-tier proving and the adapter-relayed challenge and verify calls do not expose the member's address to an eavesdropper.
- Other members of the server. This depends on the grant mechanism, not the proof. A public grant like a Discord role is visible on a member's profile to anyone in the server, so it reveals that they hold a masternode (though never which one). The Discord adapter grants per-channel, adding the member to the private channel with a per-user permission overwrite, which does not show on the public profile, so it avoids that exposure. It no longer offers a role grant mode. An adapter that grants a publicly visible marker (a role on another platform) would carry the exposure, so choose the grant surface for your exposure needs (see `adapters/discord/README.md`).

No party links a platform identity to an on-chain address FROM THE CRYPTOGRAPHY. That is the
property the design aims to provide under the proof system's assumptions, the verified parameters,
and correct software. The intended proof does not disclose the voting key or selected node. End-to-end unlinkability additionally requires that the
NETWORK PATH not undo it. The account-bearing calls are relayed by the adapter, but the two-tier
prover contacts the gateway directly on its public reads (registration and the per-epoch members
fetch), so a member who runs those on the masternode hands the gateway the node's own address. To
keep the guarantee end to end, run the two-tier prover over an anonymized path, as the party list
above and the runbook describe. Single-tier proving contacts no gateway and needs no such care.

For a member-facing explanation of setup secrets, forged admission, and chat privacy, read
[SETUP_PRIVACY.md](SETUP_PRIVACY.md). Setup randomness is not a proof-decryption key. Forged membership
can nevertheless expose private conversations to an unauthorized reader.

## What the design defends against

- Forged membership. The Merkle root is built from public DML data by a deterministic function, so anyone can recompute it and catch a snapshot whose leaves do not produce its root. Recomputation only proves internal consistency, so the gateway also requires the snapshot to carry a quorum of signatures from pinned oracle keys (`MNO_ORACLE_PUBKEYS`, `MNO_ORACLE_QUORUM`). The signature covers the root, which commits to the leaves, so a host that merely serves the JSON cannot forge a membership set, and running several independent signers means an attacker must compromise the quorum rather than one machine. The gateway refuses to start without pinned keys unless `MNO_ALLOW_UNSIGNED_ORACLE` is set.
- Replay to another account. The challenge nonce is bound to the requesting account, and the proof is bound to the nonce through the signal hash, so a proof for one account does not grant another.
- Sybil and double join. The epoch-and-context nullifier means one masternode voting key maps to one membership per epoch (see the delegation limit below).
- Stale membership. Roots are accepted only within a small recent window, and a fresh proof is required each epoch. The Discord adapter enforces this on its side with a sweep that revokes access once a member's epoch grant lapses and they have not re-verified, so a sold or banned node loses access rather than keeping a one-time grant forever. How soon depends on the mode. In single-tier mode every proof is checked against a recently published masternode list, so a sold node loses access about one epoch after it leaves the list, one week by default, plus the root window's grace. In two-tier mode the per-epoch proof shows only membership in the season's members tree, so a sold node normally keeps access until its season ends, up to 90 days by default. The two-tier epoch defaults to the season length for that reason, since a shorter epoch would not shorten this bound. The registration anchor adds a grace at the boundary. A registration may anchor to a masternode-list root up to `MNO_REGISTER_ROOT_MAX_AGE` old (900 s by default), so a node that left the list within that grace before a season boundary can still register for the next season and keep access through it. In both modes the adapter removes access at its next sweep after the grant ends, not at the instant it ends.

## Known limits, stated plainly

- Oracle trust is a pinned key, not the chain itself. Signed snapshots authenticate the leaf set against trusted oracle keys, so the membership set comes from keys the operator chose to trust, with a quorum to spread that trust across independent signers. The signature does not yet prove the leaves against the chain's own masternode-list commitment. A fully trustless check would verify the leaves against the on-chain DML commitment (the coinbase `merkleRootMNList`) under block headers verified by proof of work or a ChainLock, so no oracle key is trusted at all. That step is substantial for two reasons. The gateway would have to act as a light client, verifying headers or ChainLocks, parsing the coinbase special transaction, and reconstructing the masternode list at a height through the `protx diff` protocol. And the on-chain commitment is a SHA-256 tree over the serialized masternode entries, not the circuit's Poseidon tree over the voting-key hashes, so the two roots are not comparable directly and the on-chain set must be rebuilt and shown to match the proof tree's leaves. The signed snapshot already carries the block hash, which is the anchor that check would build on.
- The registration list is the gateway's unless the member brings their own (found 2026-09-29). To register, the prover needs the masternode list, and by default it takes that list from the gateway without checking it. Whoever can rewrite that response, the gateway's operator or a front end that ends TLS before the gateway, can serve a list holding only some masternodes and learn from whether the prover goes on to register whether the member's key is among them. Repeated, that narrows down which masternode is the member's. It cannot forge a membership or recover the key. `--node-list` closes it. The prover derives the list from a `masternodelist json` export of the member's own node, through the oracle's own derivation, and never requests the gateway's copy (`prover/masternode_list.js`). The bots' register commands include it, and a member with no node of their own drops it and is warned that the list is unchecked. The per-epoch proof has a milder form of the same exposure. It builds its path from the members tree the gateway serves, so a doctored tree could test which commitment is the member's. Commitments are not linked to masternodes, so that reveals no node, and the proof itself travels through the platform rather than back through the gateway's public route.
- Voting key, not collateral. The nullifier binds the masternode voting key the proof controls, not the collateral outpoint. The guarantee is one voting key, one membership, not one collateral, one membership. Masternodes that share a delegated voting key therefore collapse to one membership, and an operator who votes for several nodes with one delegated key gets one membership for all of them. Re-anchoring to the collateral would require the proof to bind the collateral outpoint, a larger circuit change.
- Anonymity set. Privacy is only as large as the eligible set, which is the masternode count, a few thousand. Narrowing eligibility shrinks the set and weakens privacy. In two-tier mode this applies with a further limit: the recurring per-epoch member proof is anonymous only among the members registered in that same (season, context), which can be far smaller than the full DML, down to no anonymity among member commitments when a context has a single registered member (the voting address stays hidden either way). Single-tier proofs always draw on the full eligible set.
- Timing and metadata. The cryptography hides the address link, not the fact that a member verified at a given time. Batch or delay if on-chain timing correlation is a concern.
- Nullifier griefing. Base Platform contracts use ownership-based writes, not per-type access control. The defense is that the gateway is the only writer and a nullifier is unpredictable until a valid proof is submitted, so it cannot be squatted in advance. Platform enforces uniqueness, the gateway enforces validity, and neither alone is sufficient.
- Key handling. The prover reads the raw voting key locally. It controls no funds, and it never leaves the device, but it is still a key-handling step. A variant that consumes an ECDSA signature instead keeps the key in the wallet at a higher circuit cost, and needs care to make the nullifier deterministic.
- Trusted setup. The two heavy circuits (single-tier admission and seasonal registration) are proved under Groth16, which needs a phase-two ceremony per circuit on top of the public Hermez Powers of Tau. Each setup is sound only if at least one of its contributors discarded their randomness, so the procedure in `docs/CEREMONY.md` requires at least one contributor independent of the coordinator for each, plus a public beacon. The ceremony creates no ongoing role and no view of who proves. A dishonest setup would let its contributors forge admission. It is not known to let them identify members, provided members use a proving key that verifies against the published transcript (`snarkjs zkey verify`), since Groth16's zero-knowledge holds under a subverted setup only when the key's structure is checked. The recurring two-tier members circuit stays on PLONK over the universal Hermez setup. Neither is setup-free. A backend with no trusted setup at all, a STARK or an inner-product-argument system, is the stronger option for a community tool, at a different proof size and verifier cost (see `docs/REDUCING_PROVING_COST.md`).

## Before any real deployment

Several pieces are already in place. RIPEMD-160 is implemented in-repo and the in-circuit
hash160 is validated against the generator vector on every push. The full
`mno_membership.circom` compiles against circom-ecdsa. The heavy circuits are proved under Groth16
with a per-circuit setup ceremony (`docs/CEREMONY.md`), and the members circuit under PLONK over
the public Hermez Powers of Tau.
The verification key is committed and the gateway boots with it. The oracle reads a real Dash
node and signs each snapshot, and the gateway requires a quorum of pinned oracle keys and
fails closed without them. The canonical-scalar constraint closes the nullifier malleability,
and the verifier rejects non-canonical public signals. Adapters authenticate to the gateway,
the verify binds the submitter account, and two-tier registration is durable and season-scoped
with per-context members trees. The pipeline has been exercised on real mainnet data on a
Raspberry Pi.

Three things still remain.

1. Cryptographic assurance beyond what internal checking can give. No external audit or specialist review will be commissioned. The code has had a careful adversarial self-review, and the circuits have had an internal assessment with constraint-level tools, checks against independent implementations, and the published circuit bug catalogs (`tools/circuit-analysis/RESULTS.md`). That is not an audit, and what it leaves open (the trusted-setup assumption, and no machine-checked uniqueness proof for the elliptic-curve component) stays a stated limit. `docs/SECURITY_AUDIT_SCOPE.md` is the target list those checks work from.
2. The fully trustless oracle anchor against the chain's own masternode-list commitment, described in the oracle-trust limit above. The oracle is currently trusted as a quorum of pinned keys. Verifying the ChainLock signature was prototyped as a route to this (the BLS verification and the quorum-commitment anchoring are written and tested), and it confirmed there is no shortcut. The signing quorum's key is recorded in the same block, so trusting it requires the same light-client bootstrap (a fixed checkpoint followed forward through verified history), not a self-contained signature check. See `oracle/chainlock.js` and `oracle/quorum_commitment.js` for the primitives, and `docs/HANDOFF.md` for the circular-anchoring finding.
3. The member-side cost. Each member runs the prover locally with a large proving key, which is the main adoption question to settle for a given community. The two large keys are now hosted (see `docs/PROVING_KEY.md`), and together with proving on the masternode that makes it a non-issue for an operator, and `docs/REDUCING_PROVING_COST.md` is the design track for removing the large key entirely with a different proving backend.
