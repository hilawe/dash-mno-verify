# The X11 reference harness

`common/x11/` is a JavaScript port of the eleven hash rounds Dash chains to name a block. This
directory is how that port is checked against the implementation Dash Core actually ships, and how the
committed vectors in `test/vectors/x11_round_vectors.json` are produced.

It exists because a review made the point plainly. Vectors generated by a harness nobody can run are
regression locks, not evidence: a port built wrong against a generator built wrong agrees with itself,
and nothing in the repository can tell. Everything needed to re-derive the vectors from upstream
source, and to re-run the differential fuzz, is here.

## What it does

`harness.c` links against Dash Core's own `src/crypto/x11/` sources and exposes two modes:

- `round <name> <hex>` prints the 64-byte digest of one round.
- `x11 <hex>` prints the 32-byte result of the whole chain, which is what names a block.

`generate.mjs` runs it over a fixed input set and writes the vectors file. `fuzz.mjs` runs it over
random inputs and compares each round against the JavaScript, which is the part that covers lengths
the fixed set does not.

## The reference is fetched, not vendored

The container clones Dash Core at a PINNED TAG and builds against `src/crypto/x11/` from that
checkout. Nothing from upstream is copied into this repository, which keeps the provenance a fact
about the pin rather than about whoever last updated a vendored copy. The same approach the project
already takes with `circom-ecdsa`.

The pin is `PIN`, which carries a tag and a COMMIT. The tag is how the source is found and the commit
is the pin, because a tag is mutable and a rebuild years from now has to compile the same source the
committed vectors came from. The build fetches the tag, compares the resulting commit, and FAILS if
upstream has moved it. To follow a moved tag deliberately, build with `DASH_COMMIT=` empty, read the
commit it prints, and write it into `PIN`.

The committed vectors were produced at **v23.1.3**, commit `8f06d398`.

## Running it

Docker is required, and on this project's Mac that means colima (a native `dashd` is a dead end here,
though nothing in this directory runs a node). Building the image takes a few minutes the first time.

    ./tools/x11-reference/regenerate.sh          # rebuild test/vectors/x11_round_vectors.json
    ./tools/x11-reference/fuzz.sh 200            # 200 random inputs, every round, against the reference

`regenerate.sh` writes the vectors file in place. Run the suite afterwards: if the port and the
reference still agree, nothing changes and `git diff` is empty, which is itself the result worth
having. A diff means either the port changed or the pin did, and which one it is should be obvious
from what else is in the commit.

## What the fuzz covers that the vectors do not

X11 feeds the first round 80 bytes and the other ten exactly 64, so the committed block cases exercise
every round only at those two lengths. The fuzz runs 0 to 300 bytes, which reaches the multi-block
padding paths in Grøstl and BMW that no committed vector touches. Those paths are unreachable from
X11 itself, so this is about the exported modules being correct for a caller that uses them for
something else.

## Where the anchor lives, and what runs without one

`regenerate.sh` checks the reference's own composed chain against 11 real mainnet headers, block 1 of
which points at the public Dash genesis hash. That is the anchor, and it is what catches the one
failure this directory cannot catch by construction: `harness.cpp` and `common/x11/index.js` were
written by the same author, so a CONSISTENT mistake in the round order would agree with itself and
every per-round vector would still pass.

`fuzz.sh` carries no such anchor. It compares round against round, and its handful of whole-chain
comparisons are one author's ordering against the same author's ordering. It is the right tool for
what it does, which is covering input lengths the vectors never reach, and it is not a check on the
composition. Run `regenerate.sh` for that.

Stated because a reviewer asked the question directly, and the honest answer is that the two scripts
establish different things.
